# FitConnect 보안 체크리스트

기준일: 2026-06-04
문서 상태: MVP 출시 전 점검용 초안

## 1. 릴리스 차단 항목

- [ ] 운영 환경에서 `ENVIRONMENT=production`이 설정되어 있다.
- [ ] 운영 환경에서 `ENABLE_DEMO_FALLBACK=false`가 강제된다.
- [ ] `SUPABASE_SERVICE_ROLE_KEY`가 웹/모바일 번들, 소스, 로그, 오류 리포트에 포함되지 않는다.
- [ ] 클라이언트에는 `VITE_SUPABASE_ANON_KEY` 또는 `EXPO_PUBLIC_SUPABASE_ANON_KEY`만 포함된다.
- [ ] 운영 CORS `ALLOWED_ORIGINS`는 실제 웹/관리자/모바일 딥링크 도메인만 허용한다.
- [ ] DB, Redis, Ollama, pgAdmin은 외부 인터넷에 직접 노출되지 않는다.
- [ ] 모든 외부 트래픽은 HTTPS로 종단 처리된다.
- [ ] 개인정보 처리방침, 약관, 건강 면책, 삭제 요청 경로가 공개되어 있다.

## 2. 인증과 세션

- [ ] 이메일/비밀번호 로그인 실패 시 과도한 상세 오류를 반환하지 않는다.
- [ ] Kakao OAuth 실패 시 access token, OAuth 응답 원문, 사용자 정보를 로그에 남기지 않는다.
- [ ] access token은 HTTPS를 통해서만 전달된다.
- [ ] refresh token 저장 방식은 플랫폼 보안 저장소를 사용한다.
- [ ] 인증 API에 rate limit이 적용된다.
- [ ] 토큰 만료, 로그아웃, 탈퇴 후 보호 API 호출이 실패한다.
- [ ] 관리자 권한은 클라이언트 표시뿐 아니라 서버에서 검증한다.

## 3. 권한과 RLS

- [ ] `profiles` 공개 조회 범위가 제품 정책과 맞다. 전화번호, 이메일 등 공개하면 안 되는 필드는 별도 API에서 제한한다.
- [ ] `diet_logs`, `workout_logs`, `chat_messages`, `notifications`, `clothing_recommendations`는 본인 데이터만 접근된다.
- [ ] `bookings`는 예약 사용자와 코치만 조회/수정할 수 있다.
- [ ] `payments`는 사용자 본인 조회와 서버 전용 쓰기 정책이 분리되어 있다.
- [ ] `rag_documents` 쓰기 정책은 운영에서 서버 전용으로 제한된다.
- [ ] Supabase anon key로 각 테이블에 대해 select/insert/update/delete 권한 테스트를 수행했다.
- [ ] service role key를 사용하는 Node BFF/FastAPI 엔드포인트는 자체 권한 검증을 수행한다.

## 4. API와 입력 검증

- [ ] 예약 생성 시 시간, 가격, 코치 존재 여부, 중복 예약을 서버에서 검증한다.
- [ ] 예약 상태 변경은 사용자와 코치 역할별 허용 상태를 제한한다.
- [ ] 식단 채팅 메시지 길이 제한과 악성 입력 방어가 있다.
- [ ] 자유 입력란에는 주민등록번호, 결제정보, 진단서, 처방전 입력 금지 안내가 있다.
- [ ] 의류 추천 클릭 API는 본인 추천 ID만 갱신한다.
- [ ] 관리자 API는 페이지네이션, 필터, 권한 검증을 갖춘다.
- [ ] 모든 오류 응답은 내부 stack trace와 secret 값을 포함하지 않는다.

## 5. 파일과 이미지 업로드

- [ ] 음식 이미지 업로드는 5MB 이하로 제한된다.
- [ ] `image/*` MIME 검증 외에 실제 파일 시그니처 검증을 추가한다.
- [ ] 이미지 원본 저장 여부를 명확히 정한다. 저장하지 않는 구조를 우선한다.
- [ ] 저장 시 object ACL은 비공개로 설정하고 서명 URL 만료 시간을 제한한다.
- [ ] 이미지 분석 요청/응답 원문이 로그에 남지 않는다.
- [ ] 악성 파일, polyglot 파일, EXIF 개인정보 제거 정책을 검토한다.

## 6. AI와 건강 안전

- [ ] AI 응답은 의료 진단, 치료, 처방, 질병 완치 보장 표현을 피한다.
- [ ] 식단 AI 화면에 건강 면책 문구가 표시된다.
- [ ] 고위험 사용자에게 전문가 상담 안내가 표시된다.
- [ ] 사용자가 질병명, 약물, 검사 결과를 입력하지 않도록 안내한다.
- [ ] 외부 LLM 도입 시 전송 항목, 리전, 보관 정책, 학습 사용 여부를 검토한다.
- [ ] RAG 문서에는 개인정보, 저작권 침해 자료, 검증되지 않은 의료 지시가 포함되지 않는다.

## 7. 로그와 모니터링

- [ ] 로그 마스킹 규칙에 이메일, 전화번호, 토큰, key, OAuth token, 결제 key, 식단 대화 원문이 포함된다.
- [ ] API 401/403/429/5xx 비율을 모니터링한다.
- [ ] 관리자 로그인 실패, 권한 오류, 대량 조회를 알림으로 감지한다.
- [ ] DB 쿼리 오류에 개인정보 원문이 포함되지 않는다.
- [ ] 보안 로그 보관 기간과 접근 권한이 문서화되어 있다.

## 8. 인프라

- [ ] Nginx 보안 헤더가 적용된다. `X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy` 검토
- [ ] WebSocket 경로는 인증과 origin 검증을 적용한다.
- [ ] Redis는 인증과 내부 네트워크 제한을 적용한다.
- [ ] Ollama는 내부 네트워크에서만 접근 가능하다.
- [ ] PostgreSQL은 백업, 암호, 네트워크 접근 제한이 설정되어 있다.
- [ ] Docker image build context에 `.env`, `node_modules`, `.venv`, secret 파일이 들어가지 않는다.
- [ ] 컨테이너는 불필요한 root 권한과 write 권한을 줄인다.

## 9. 프론트엔드와 모바일

- [ ] Vite 빌드 산출물에서 `SUPABASE_SERVICE_ROLE_KEY`, `JWT_SECRET`, OAuth secret 문자열이 검색되지 않는다.
- [ ] Expo public env에는 공개 가능한 값만 포함된다.
- [ ] 모바일 deep link, push payload에 민감정보가 포함되지 않는다.
- [ ] 클라이언트 라우팅으로 숨긴 관리자 화면은 서버 권한 없이 데이터를 가져오지 못한다.
- [ ] 로컬 스토리지나 AsyncStorage에는 민감정보를 최소화한다.

## 10. 의존성과 공급망

- [ ] `npm audit`, `pip-audit` 또는 대체 도구로 취약점 점검을 수행한다.
- [ ] lockfile 변경은 리뷰한다.
- [ ] 서드파티 SDK의 개인정보 수집표를 보관한다.
- [ ] Apple privacy manifest와 Google Data safety 입력이 SDK와 일치한다.
- [ ] CI/CD secret은 pull request 로그에 노출되지 않는다.

## 11. 개인정보와 법정 고지

- [ ] 개인정보 처리방침 공개 URL이 앱스토어와 서비스 내에 연결되어 있다.
- [ ] 데이터 삭제 요청 경로가 사용자에게 쉽게 보인다.
- [ ] 개인정보 유출 신고 판단 기준과 담당자가 지정되어 있다.
- [ ] 만 14세 미만 처리 정책이 제품 UX와 일치한다.
- [ ] 제3자 제공, 처리위탁, 국외 이전 표가 실제 사업자와 일치한다.
- [ ] Apple/Google 개인정보 표시가 실제 수집/공유와 일치한다.

## 12. 릴리스 후 점검

- [ ] 배포 후 30분 동안 error rate, latency, auth failure, RLS error를 관찰한다.
- [ ] 새 빌드에서 가입, 로그인, 예약, 식단 채팅, 이미지 분석, 의류 추천 smoke test를 실행한다.
- [ ] 로그에 secret 또는 개인정보 원문이 남지 않는지 샘플링한다.
- [ ] 보안 이벤트 또는 개인정보 문의 채널이 정상 동작한다.
- [ ] 실패 시 이전 이미지와 DB 백업으로 롤백할 담당자가 지정되어 있다.
