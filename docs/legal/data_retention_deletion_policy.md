# FitConnect 데이터 보관 및 삭제 정책 초안

기준일: 2026-06-04
문서 상태: 초안. 출시 전 법무 검토, 실제 DB 마이그레이션, Supabase Auth 삭제 절차, 백업 정책, 앱 내 삭제 UI 구현이 필요합니다.

## 1. 원칙

- 목적 제한: 수집 목적이 끝난 데이터는 삭제하거나 익명화합니다.
- 최소 보관: 서비스 제공, 보안, 법령상 의무, 분쟁 대응에 필요한 기간만 보관합니다.
- 분리 보관: 법령상 보관이 필요한 데이터는 일반 서비스 데이터와 논리적으로 분리합니다.
- 사용자 통제: 사용자가 열람, 정정, 삭제, 처리정지를 요청할 수 있는 절차를 제공합니다.
- 추적 가능성: 삭제 요청, 처리 결과, 보류 사유를 내부 기록으로 남깁니다.

## 2. 데이터별 보관 기준

| 데이터 | 현재 저장 위치 | 기본 보관 기간 | 삭제/익명화 기준 | 비고 |
| --- | --- | --- | --- | --- |
| 계정/Auth | Supabase Auth, `profiles` | 회원 탈퇴 시까지 | 탈퇴 요청 후 30일 이내 삭제. 부정 이용 방지 목적 식별자는 별도 해시로 최대 1년 보관 검토 | Auth provider 삭제 API 연동 필요 |
| 프로필 | `profiles` | 회원 탈퇴 시까지 | 삭제 또는 익명화 | 이름, 전화번호, 운동 목표, 선호 운동 포함 |
| 코치 프로필 | `coach_details`, `gyms` | 코치 탈퇴 또는 계약 종료 시까지 | 공개 노출 중단 후 계약/분쟁 보관 기간 종료 시 삭제 | 자격 정보 검증 자료 보관 기준 별도 검토 |
| 예약 | `bookings` | 예약 종료 후 3년 권장 | 법령/분쟁 보관 기간 종료 후 익명화 또는 삭제 | 요청 메모, 코치 메모는 민감정보 입력 가능성이 있어 최소화 필요 |
| 결제/정산 | `payments` | 결제 또는 정산 완료 후 5년 권장 | 법령상 보관 기간 종료 후 삭제 | 전자상거래, 세무, 회계 보관 의무 검토 필요 |
| 리뷰 | `reviews` | 게시 중 또는 계정 유지 기간 | 사용자가 삭제하거나 탈퇴 시 익명화. 분쟁 관련 리뷰는 최대 3년 보관 검토 | 공개 리뷰는 작성자 표시 범위 제한 |
| 식단 로그 | `diet_logs` | 사용자가 삭제하거나 탈퇴할 때까지 | 요청 후 30일 이내 삭제 | 음식명, 칼로리, 영양소, AI 분석 결과 |
| 식단/운동 채팅 | `chat_messages` | 사용자가 삭제하거나 탈퇴할 때까지. 기본 1년 자동 삭제 권장 | 요청 후 30일 이내 삭제 또는 세션 단위 삭제 | 질병명 등 민감정보 임의 입력 가능성 있음 |
| 음식 이미지 | API 응답, 향후 스토리지 | 분석 완료 후 저장하지 않는 구조 권장. 저장 시 사용자가 삭제할 때까지 | 원본 저장 최소화, 썸네일/분석 결과 분리 | 현재 API는 data URL 응답을 생성하므로 로그 저장 금지 |
| 운동 로그 | `workout_logs` | 사용자가 삭제하거나 탈퇴할 때까지 | 요청 후 30일 이내 삭제 | 자세 점수 등 건강 관련 추론 가능 |
| 의류 추천/클릭 | `clothing_recommendations` | 생성 후 1년 권장 | 1년 후 익명 통계화 | 구매 전환 저장 시 제휴/광고 고지 필요 |
| 알림 | `notifications` | 생성 후 1년 권장 | 1년 후 삭제 또는 사용자가 삭제 | 보안/거래 알림은 분쟁 기간 보관 검토 |
| RAG 문서 | `rag_documents` | 문서 유효 기간 | 개인정보 포함 시 즉시 제거 | 원칙적으로 개인정보를 포함하지 않음 |
| 기술 로그 | 서버/Nginx/호스팅 로그 | 90일 권장 | 기간 만료 시 순환 삭제 | IP, User-Agent, 오류 메타데이터 포함 가능 |
| 보안 감사 로그 | 서버/관리 시스템 | 1년 권장 | 기간 만료 시 삭제 또는 익명화 | 관리자 접근, 권한 변경, 실패 로그인 |
| 고객지원 문의 | 고객지원 도구, 이메일 | 처리 완료 후 3년 권장 | 기간 만료 시 삭제 | 분쟁, 환불, 권리행사 이력 포함 가능 |
| 백업 | DB/스토리지 백업 | 30-90일 권장 | 백업 만료 시 자동 삭제 | 삭제 요청 후에도 백업 만료 전까지 복구본에 남을 수 있음 |

권장 기간은 MVP 운영 기준입니다. 실제 서비스 유형, 결제 도입, 통신판매 여부, 세무 의무, 분쟁 처리 정책에 따라 조정해야 합니다.

## 3. 삭제 요청 처리 절차

1. 접수: 앱 설정, 이메일, 고객지원 채널로 요청을 받습니다.
2. 본인 확인: 계정 로그인 상태, 이메일 인증, 추가 확인 절차를 사용합니다.
3. 범위 확인: 전체 탈퇴, 특정 식단 로그, 특정 채팅 세션, 특정 리뷰 등 삭제 범위를 확인합니다.
4. 보류 사유 확인: 결제/환불, 분쟁, 법령상 보관, 보안 사고 조사 등 보류 사유가 있는지 확인합니다.
5. 실행: 운영 DB, Supabase Auth, 스토리지, 검색 인덱스, 캐시, 알림 토큰, 고객지원 도구에서 삭제합니다.
6. 수탁자 전달: 삭제가 필요한 수탁자 또는 제3자에게 요청을 전달합니다.
7. 완료 통지: 처리 결과, 보류 항목, 보류 기간을 사용자에게 안내합니다.
8. 기록: 요청 시각, 처리자, 처리 결과, 예외 사유를 감사 로그에 남깁니다.

## 4. 계정 탈퇴 처리

계정 탈퇴 시 기본 처리:

- Supabase Auth 사용자 삭제 또는 비활성화
- `profiles` 삭제. FK `ON DELETE CASCADE`가 연결된 데이터 삭제 여부 확인
- 식단 로그, 운동 로그, 채팅, 추천, 알림 삭제
- 예약, 결제, 리뷰는 법령/분쟁/정산 목적이 있으면 분리 보관 또는 익명화
- 코치 회원은 진행 중 예약, 정산, 고객 문의가 있으면 즉시 삭제가 제한될 수 있음

구현 체크:

- [ ] Supabase Auth delete user API를 서버 전용 service role로만 호출한다.
- [ ] 탈퇴 API는 본인 인증과 최근 로그인 확인을 요구한다.
- [ ] 탈퇴 처리 전 진행 중 예약과 결제 상태를 확인한다.
- [ ] 삭제 후 캐시와 검색 인덱스를 무효화한다.
- [ ] 백업 만료 일정을 사용자에게 안내한다.

## 5. 자동 삭제 작업

운영 배포 전 다음 배치 작업을 준비합니다.

- 오래된 `chat_messages` 삭제 또는 익명화
- 오래된 `notifications` 삭제
- 오래된 `clothing_recommendations` 익명 통계화
- 기술 로그와 보안 로그 순환 삭제
- 탈퇴 후 보류 기간이 끝난 예약/결제/문의 기록 삭제
- RAG 문서 내 개인정보 스캔

## 6. 파기 방법

- DB 레코드: 삭제 쿼리 또는 식별자 제거 후 익명화
- 파일/이미지: 스토리지 객체 삭제와 CDN 캐시 무효화
- 로그: 보관 기간별 log rotation과 secure delete가 가능한 저장소 정책 적용
- 출력물: 분쇄 또는 소각
- 백업: 백업 만료 정책에 따른 자동 삭제. 백업에서 개별 레코드만 즉시 삭제하기 어려운 경우 접근을 제한하고 복원 시 삭제 요청을 재적용

## 7. 보류와 예외

다음 경우 삭제 요청을 즉시 완료하지 못할 수 있습니다.

- 결제, 환불, 세금, 회계, 소비자 분쟁 대응에 필요한 기록
- 진행 중 예약 또는 코치 정산
- 보안 사고 조사, 부정 이용 방지
- 법령상 보관 의무 또는 감독기관 요청
- 백업 만료 전 복구본

보류 시 사용자에게 보류 항목, 사유, 예상 종료 시점을 안내합니다.

- 삭제 실패 건수와 재처리 건수
